# 方案定稿报告：矿主优先 · 相似节点候选 · 诚实参考推荐

> 日期：以对话拍板为准
> 状态：设计定稿，尚未端到端重跑
> 执行目录：本仓库根目录（wcx）

## 1. 已拍板的决策

| 决策项 | 定稿结论 |
|---|---|
| 数据口径 | **7 天累计**（2026-03 起、约 5% 抽样、满 7 天账），不切日粒度/单位带宽 |
| 金额验证 | 反事实遮挡（节点内藏已跑业务）可用，金额以 **WAPE/R²** 为主要指标 |
| 冷启动定位 | **候选 / 参考**，不承诺“最赚”，明确标注不确定性 |
| 平台利润 | **软约束**：负利润降权，但仍可进 Top2/3（标注风险） |
| 交付物 | 模型 + 机器可读指标 + 报告 + **HTML 可视化** |

## 2. 一句话方案

> 用相似节点真实跑过的业务做候选，在候选内按“矿主 7 天结算最大化”排序，平台利润为负只降权不删除，输出 Top3 + 金额/利润/容量参考 + HTML 展示，定位为人工决策的候选参考。

## 3. 设计要点

| 本方案的设计要点 | 说明 |
|---|---|
| 候选须有真实证据 | 候选 = 相似节点真实跑过（满 7 天账）的业务 ∪ 节点自身历史账 |
| 目标明确矿主优先 | 排序主序 = 矿主 7 天结算；平台利润仅作软约束 |
| 平台利润软约束 | pred_profit<=0 降权但不删除，标注风险 |
| 诚实标注不确定性 | 定位为候选/参考，不承诺最赚 |

## 4. 模型流程（已落地为主版脚本，见 02_main_recommendation/stage_e2e.py）

```
输入新节点 node_id
 → 节点画像（nodes_attr_filled.csv）
 → 相似节点召回（节点固有特征余弦，TopK=10~30）
 → 候选 = 相似节点真实跑过且满7天账的业务 ∪ 该节点自己历史账（若有）
 → 特征 = 节点固有属性 + 业务统计（平均结算/利润/支持度/容量状态）
 → 排序分 = 矿主预测7天结算（主序）
     + 平台利润软约束（pred_profit<=0 时降权，不删除）
     + 容量软参考（超容量业务降权/标注）
 → 输出 Top1~Top3：业务、名称、预测结算、预测利润、利润正负、容量状态
 → 输出为 CSV + JSON 指标 + HTML 总览
```

## 5. 验证与指标

- **金额验证**：节点内反事实遮挡（隐藏该节点一条已跑业务），报 WAPE / R² / MAE；该口径证明“估已跑业务的金额”能力。
- **候选可行性**（不作为主尺子，因为冷启动没有反事实真值）：
  - 每节点候选数覆盖率；
  - Top1 平台利润为正比例；
  - 推荐业务在相似节点上的结算分位；
  - Top1 集中度（占比 / HHI，只诊断不硬压）。
- **明确不做的**：不以“命中实际被分配业务”当作有效性证据（该口径对推荐不公平，已在诊断中证明会误导）。

## 6. 交付物

| 类型 | 产物 |
|---|---|
| 模型 | 相似节点召回索引 + 排序/回归模型（见 `02_main_recommendation/`） |
| 数据 | 每节点候选 + Top3 结果 CSV |
| 指标 | 机器可读 JSON（金额 WAPE/R²、候选覆盖率、利润为正比例、集中度） |
| 报告 | 本文件 + 结果说明 |
| HTML | 推荐总览页（离线，可搜索/筛选） |

## 7. 已知局限

1. 冷启动无真实“未跑业务收益”标签，“更赚”是基于相似节点统计的参考判断。
2. 相似节点信号在诊断中单独命中低，需与其他信号（热度/业务统计）组合使用，不单靠它。
3. 平台利润预测本身 R² 弱，利润约束依赖业务统计 + 预测混合判断。
4. 容量为近7天流量近似，非客户真实容量。

## 8. 当前最不确定、拿不准的点

1. 本方案的设计基线（候选须真实证据 + 矿主优先 + 平台软约束 + 诚实候选定位）是否为评审认可的方向，仍需确认或修正。
2. 相似节点 TopK、候选并集范围、平台利润软约束的具体降权系数尚未校准，需用反事实遮挡与候选质量做一次实验再定。
3. 相似节点单独命中低（≈0%），组合后能否把候选质量做起来尚未端到端验证。
4. HTML 可视化应做到“带容量/利润/区间的完整决策页”还是“离线 Top3 总览表”即可——两版工作量和观感差别较大，需明确期望。
