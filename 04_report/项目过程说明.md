# 项目过程说明（详细版）

> 本文档按时间顺序完整记录“矿主优先·相似节点候选·诚实参考推荐”项目的设计与迭代过程，
> 供汇报、交接与答辩使用。数据与数字均可由 `run_verify_all.py` 复现。

## 0. 背景与起点

- 项目要回答的业务问题：一个矿机节点上线后，跑哪个业务更能让**矿主多拿结算**，同时**平台利润不为负**。
- 工作起点：先明确问题与数据口径，再搭建一条“可复现、可解释、对冷启动诚实”的推荐路线。

## 1. 阶段一：理解问题与数据口径

### 1.1 数据来源
- 金额与带宽：Superset 宽表 `test.node_day_ops_wide_full`
- 节点属性：Superset `jarvis.node_analysis_data / node_join / dial_acc`
- 带宽历史/容量：宽表日 `peak95`（近 7 天）

### 1.2 关键口径约定
- 样本：约 5% 节点抽样（后缀 00–0c），时间窗 2026-03-16 起，取“业务首次出现日后满 7 天账”。
- 矿主结算 = `cost_finalAmount`；平台利润 = `revenue_finalAmount − cost_finalAmount`。
- 数据为本项目独立拉取加工，口径以本文档与 `05_shared_data/DATA_README.md` 为准。

### 1.3 一开始就做的关键判断
- “命中”有多种定义（历史跑得最多 / 金额排序 / 历史当天实际分配等），口径不同不可直接比较，汇报前必须先说明所采用的尺子。
- 若用随机切分，训练会见过与测试相似的节点，**高估真实效果**；因此本项目采用**时间外切分**做验证。

## 2. 阶段二：数据准备

- 用 Superset API（脚本自动登录 → 执行 SELECT → 落 CSV）拉取：
  - 节点×业务满 7 天账（成本/收入）
  - 节点画像（含缺失回填）
  - 近 7 天日 95 带宽
  - 业务名补齐
- 对画像缺失字段做了回填（node_join/HRR 快照兜底）。
- 产物：`outcomes_7d_named.csv`、`nodes_attr_filled.csv`、`bw_daily_7d.csv`、
  `business_capacity_summary.csv`。

## 3. 阶段三：早期复现与试错

### 3.1 早期金额基线（遮挡口径）
- 用反事实/遮挡思路建立成本金额回归基线：WAPE≈0.57、R²≈0.64，作为金额模型起点。

### 3.2 尝试“全候选打分”
- 把候选扩到所有训练中高频业务，直接按金额排序。
- 结果：几乎所有节点都指向少数“全局高结算”业务，命中极低（≈0）。
- 结论：**不限定候选会退化为“热门先验”，个性化消失。**

### 3.3 尝试“候选收紧 / Top1 必须历史”
- 改为只在该节点已跑过（或相似节点跑过）的业务里选，命中明显回升。
- 缺点：对“真正没跑过、但可能更赚”的业务不友好，属于用规则保稳。

### 3.4 尝试“双塔召回”
- 训练节点/业务表示再召回候选（随机切分下有效）。
- 在**时间外冷启动**测试下没有明显增益；且相似节点单独命中也低。
- 结论：双塔可作为结构探索，但不能解决“冷启动缺真值”的根因。

### 3.5 其它消融（全部留下结论）
- 反先验/放大惩罚：命中不升反降。
- 带宽辅助分：开/关几乎无差异（17/1035 节点才有自身账数据）。
- log1p 金额目标：降低 WAPE 但牺牲 R²（金额更稳、排序命中略降）。
- 单位带宽目标：因缺真实 `buildBandwidth`，用名义带宽近似后命中下降，仅作参照尺子。

## 4. 阶段四：收敛为主版

### 4.1 主版思路
```
输入 node_id
 → 节点画像
 → 相似节点召回（画像余弦 Top15）
 → 候选 = 相似节点真实跑过的业务 ∪ 该节点自身满 7 天账
 → XGB 预测 7 天成本/利润（时间外训练）
 → 排序：矿主预测结算主序 + 平台利润<=0 软降权 + 容量超限软降权
 → 输出 Top1~3（含预测矿主结算与平台利润）
```

### 4.2 主版结果（时间外新节点，训练期未见）
| 指标 | 数值 | 含义 |
|---|---:|---|
| 真实最优进 Top1 | 35.9% | 历史被分配且结算最高业务是否被排第一 |
| 真实最优进 Top3 | 65.4% | 进前三 |
| Top1 平台利润为正 | ≈100% | 软约束下基本不选负利润 |
| 矿主结算预测 WAPE | ≈0.82 | 金额偏粗，只作排序参考 |

### 4.3 主版为什么可信
- 时间外切分：训练未见过测试节点。
- `run_verify_all.py` 可一键复现并核验关键数字。
- 把“命中被分配业务”当作候选质量信号，而不是收益证明。

## 6. 现状与边界（诚实声明）

- 定位是“候选/参考”系统，**不承诺换业务一定更赚**。
- 金额预测 WAPE≈0.82，仅供排序参考。
- 无真实 `buildBandwidth`/客户容量，单位带宽与容量约束只能做参照或示意。
- 未上线、未做小流量 A/B、不自动切换。

## 7. 关键结论（供汇报）

1. 推荐集中/命中高 ≠ 更赚；冷启动无真实反事实标签，任何方案都只是参考。
2. 方案要点：时间外验证 + 平台不亏软约束 + 可复现 + 诚实边界。
3. 金额误差、真实建设带宽/容量缺失是主要短板，也是下一步要做的事。
4. 要“证明换业务更赚”，只能做受控小流量上线 A/B——离线模型无法单独证明。

## 8. 下一步建议（若继续）

- P0：接入真实 `buildBandwidth` 与客户容量，升级单位带宽尺子。
- P0：设计低风险节点小流量 A/B（随机切推荐 vs 保持，比真实 7 天结算与平台利润）。
- P1：补齐训练侧画像覆盖；做多窗口滚动回测；把决策名单做成人工复核表。
